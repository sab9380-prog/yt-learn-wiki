# AWS 엔지니어가 공개한 아마존 내부 데이터 — 4.5배 빨라진 25개 팀의 습관 5가지

## 🧠 이해 (Understand)
- **Summary:** 아마존이 50개 팀을 1년간 관찰한 결과, 같은 AI 코딩 도구를 써도 일하는 방식을 의도적으로 바꾼 팀(4.5배↑)과 기존 방식 위에 도구만 얹은 팀(3배 미만)으로 뚜렷이 나뉘었다. 4.5배 팀의 공통 습관은 ①에이전트 컨텍스트 문서화 ②초기 생산성 하락 감수 ③자기 검증 조건 부여(베이비시팅 탈출) ④코드 전 스펙 작성 ⑤테스트 선행이다. 그러나 이 습관을 실행하면 번아웃·조직 조급함·결정 병목이라는 새 문제가 따라온다. 특히 코드가 한두 달로 단축되면서 '결정하는 시간'이 새로운 가장 긴 병목이 됐다. 아마존의 결론: 도구는 같았고, 갈린 건 일하는 방식을 의도적으로 바꿨느냐였다.
- **Core Message:** AI 코딩 도구의 성과는 도구가 아니라 일하는 방식을 의도적으로 바꿨느냐에 달려 있다.
> 프론티어 개발자는 코드의 1~2%만 직접 쓰고 나머지는 에이전트가 쓴다.
> 도구를 기존 방식 위에 뿌린 팀과 일하는 방식 자체를 바꾼 팀 — 이게 갈린 이유였다.
> 프론티어 팀은 코드 쓰는 시간보다 결정하는 시간이 더 길다.
❗ 베드록 팀은 30명·18개월 예상 작업을 6명·76일 만에 완료했다(최대 20배 생산성).
❗ 4.5배 팀의 거의 모두가 에이전트 도입 초기에 생산성이 먼저 떨어졌다고 답했다.
❗ 타입 안전성 때문에 Python·JavaScript에서 TypeScript·Rust로 프로그래밍 언어 자체를 바꾼 팀이 아마존 내부에 실제로 존재한다.

## 📚 핵심 용어
- **프론티어 개발(Frontier Development):** 코드의 1~2%만 직접 쓰고 나머지는 에이전트가 수 시간 자율 실행하며, 여러 에이전트를 동시에 병렬로 운영하는 개발 방식. / 공장장처럼 기계 여러 대를 동시에 돌리되 직접 나사를 조이지 않는 것. 내 손이 아닌 판단력이 생산을 결정한다. / 바이브 코딩은 에이전트와 계속 대화하며 내가 루프 안에 있지만, 프론티어 개발은 에이전트를 설정하고 루프 밖으로 나와 다른 일을 병행한다.
- **자기 검증 조건 부여:** 에이전트에게 할 일뿐 아니라 '완료됐다는 걸 스스로 어떻게 확인할지' 기준을 함께 주어 에이전트가 자율 수정하게 하는 방법. / 심부름을 보낼 때 '우유 사 와'가 아니라 '유통기한 1주 이상짜리로, 영수증 찍어서 확인해 줘'라고 하는 것. / 베이비시팅은 매 단계마다 내가 확인·승인하지만, 자기 검증 조건 부여는 에이전트가 기준을 충족할 때만 나에게 돌아온다.
- **느려져야 빨라진다:** 에이전트가 기존 코드베이스에서 잘 작동하려면 컨텍스트 구축·에러 메시지 개선·도구 정비 등 선행 투자가 필요해 초기에 생산성이 일시 하락하는 현상. / 밭에 씨 뿌리기 전 땅을 먼저 갈아엎는 것. 그 며칠이 느리지만 그래야 수확이 커진다. / 일반적인 생산성 향상은 도구를 추가하면 즉시 빨라지지만, 이 개념은 의도적 선행 투자 기간을 거쳐야 비로소 큰 도약이 가능하다는 점이 다르다.
- **결정 병목:** 코딩 속도가 크게 빨라지면서 제품 출시의 가장 느린 구간이 '만들지 말지 결정'과 '출시 승인' 프로세스로 이동하는 현상. / 고속도로는 넓어졌는데 톨게이트 차선이 그대로라 오히려 거기서 막히는 것. / 기존 병목은 코드 작성(9~12개월)이었지만, 결정 병목은 의사결정·승인 프로세스(2+2개월)가 전체 일정을 지배하는 구조적 차이가 있다.
