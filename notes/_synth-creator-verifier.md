# Creator-Verifier 패턴

## 핵심 원리 (모든 노트가 동의하는 것)

**"만든 사람이 검증하면 안 된다."**

작업을 수행한 에이전트(또는 모델)와 **별개의 독립된 에이전트**가 결과를 검증하는 이중 확인 구조다. 자기가 쓴 글의 오탈자를 못 찾는 것처럼, 작성자는 자기 결과의 오류를 잘 못 찾는다 — 독립된 제3자 교열이 필요한 이유다. [[2026-07-03-유능한-페이블을-바보로-만들지-마세요-명령은-줄이고-이유를-말하세요]]

## 노트별 강조 관점

|------|------|------|
| **동일 모델, 다른 인스턴스** | 새 대화(새 에이전트)에 동일 요구사항을 붙여 독립 검증 — 앤트로픽 실험에서 '도구 실행 결과와 대조' 지시 하나만으로 근거 없는 완료 보고가 거의 사라짐 | [[2026-07-03-유능한-페이블을-바보로-만들지-마세요-명령은-줄이고-이유를-말하세요]] |
| **적대적 검토(Adversarial Review)** | AI가 낸 답을 다른 AI가 의심하며 재검증 → 정확도 +6%, 단 응답시간 +72%의 트레이드오프 존재 | [[2026-06-25-진짜는-에이전트가-아니라-스킬-이었다]], [[2026-06-08-진짜는-에이전트가-아니라-스킬-이었다]] |
| **다른 회사 모델 교차 검증** | 같은 회사 모델은 같은 곳에서 실수함 → 오프스가 플랜, 코덱스가 adversarial review로 약점을 상호 보완 | [[2026-05-22-클로드-코드-하나만-쓰면-이제-망합니다-feat-Codex]] |
| **멀티 에이전트 교차 검증** | 다이나믹 워크플로우에서 여러 에이전트가 서로 결과를 검토·반박해 품질 향상 | [[2026-06-01-아직도-클로드코드에-외부-툴-붙이세요-이제-다-안에-있습니다]] |
| **루프 시스템의 검증 단계** | 평가→개선→**검증**→적용 순환 구조의 핵심 고리로 작동, 측정 없는 진화는 금지 | [[2026-06-09-AI를-자동으로-진화시키는-법]] |
| **프레임워크 선택 기준** | 제어 가능성·가시성·상태 관리가 보장되는 환경에서만 Creator-Verifier가 안정적으로 작동 | [[2026-05-22-RISK-AI-에이전트-프레임워크를-잘못-고르면-2026년-프로젝트는]] |

## 실전 적용

- **즉시**: 중요 결과물을 받으면 동일 요구사항을 **새 대화**에 붙여넣어 독립 검증 (추가 시간 10~15분) [[2026-07-03-유능한-페이블을-바보로-만들지-마세요-명령은-줄이고-이유를-말하세요]]
- **비용 최적화**: 설계(오프스) → 검증(코덱스 adversarial review) → 구현(소넷) 순서로 비용을 1/3로 절감 [[2026-05-22-클로드-코드-하나만-쓰면-이제-망합니다-feat-Codex]]
- **속도 트레이드오프 인지**: 검증을 넣으면 정확도는 오르지만 시간은 늘어남 — 중요도에 따라 적용 여부 판단 [[2026-06-25-진짜는-에이전트가-아니라-스킬-이었다]]

---

## ⚠️ 주의점

검증자 자체가 낡거나 부실하면 의미 없다. 스킬 문서가 낡으면 한 달 만에 정확도가 95%→65%로 추락했듯, **검증 기준과 컨텍스트도 최신 상태를 유지**해야 한다. [[2026-06-08-진짜는-에이전트가-아니라-스킬-이었다]]

---

## 한 줄 정의

> **Creator-Verifier 패턴**이란, AI가 만든 결과를 그 AI가 직접 검증하지 않고 독립된 별개의 에이전트(또는 다른 모델)가 재검증하여 자기검증 편향을 제거하는 이중 확인 구조다.
