# 바이브코딩 보안 실수 3가지

## 🧠 이해 (Understand)
- **Summary:** AI로 만든 앱의 절반 이상이 해킹 가능한 상태라는 보안 연구 결과를 바탕으로, 바이브코딩 시대 가장 흔한 보안 실수 3가지를 분석합니다. RLS(Row Level Security) 잘못 설정으로 사용자가 자기 구독 상태를 프리미엄으로 바꿔 만 달러 청구서가 날아올 뻔한 사례, Rate Limit 미설정으로 백엔드가 직접 공격당하는 문제, 프론트엔드에서 민감한 API 키를 직접 호출해 유출되는 위험을 설명합니다. AI가 기능은 만들어주지만 보안 설정은 빠뜨리는 경우가 많고, 환경변수도 프론트엔드에서는 추출 가능하다고 경고합니다. 해결책으로 구체적 시나리오 기반 RLS 감사, 백엔드 Rate Limit 설정, 민감한 API의 백엔드 전용 호출과 예산 한도 설정을 제시합니다.
- **Core Message:** AI가 기능은 만들어주지만 보안은 사람이 직접 체크해야 하며, '딸깍 한 번이면 끝'이라는 환상을 버리고 의도적으로 보안 대화를 나눠야 한다.
> AI의 '완료'와 내 '완료'는 기준이 다릅니다. AI의 완료는 기능이 돌아가는 거고 내 완료는 해킹 불가능한 상태여야 해요.
> 코딩은 전체의 10%예요. 이런 설정이 나머지 90%입니다.
> 앱이 잠깐 죽는 게 만 달러 청구서보다 백 배 낫습니다.
❗ AI로 만든 앱 20,000개 중 11%가 데이터베이스 비밀번호를 프론트엔드에 그대로 노출하고, 그중 83%는 접근 제어가 아예 없었음
❗ Lovable으로 만든 앱에서 인증 로직이 거꾸로 작동해 정상 사용자는 차단하고 공격자는 접근 가능한 상태가 됨
❗ 프론트엔드와 모바일 앱의 환경변수는 전부 추출 가능하며, 환경변수가 안전한 곳은 백엔드뿐

## 📚 핵심 용어
- **RLS (Row Level Security):** 데이터베이스에서 사용자가 자신의 데이터만 볼 수 있도록 제한하는 보안 규칙 / 회사 사무실 출입증과 같다. 자기 부서 문만 열리고 다른 부서는 접근 불가하듯, 자기 데이터만 볼 수 있게 제한한다. / SQL 문법과 RLS 설계의 차이 — SQL은 AI가 써주지만, 어떤 데이터를 어떤 테이블에 분리할지는 전체 플로우를 이해하는 사람이 판단해야 한다.
- **Rate Limit:** 특정 시간 내 API 호출 횟수를 제한하여 남용을 방지하는 보안 기법 / ATM 출금 한도와 같다. 하루에 몇 번만 출금 가능하듯, API도 시간당 호출 횟수를 제한해 무분별한 사용을 막는다. / 프론트엔드 제한과 백엔드 제한의 차이 — 프론트엔드 제한은 개발자 도구로 우회 가능하지만, 백엔드 제한은 우회 불가능하다.
- **바이브코딩:** AI를 활용해 빠르게 애플리케이션을 개발하는 방식 / 인스턴트 요리와 같다. 재료만 넣으면 빠르게 완성되지만, 간을 맞추고 영양을 고려하는 건 요리사가 해야 한다. / 전통 개발과 바이브코딩의 차이 — 전통 개발은 처음부터 보안을 고려하지만, 바이브코딩은 기능 구현 후 보안을 별도로 체크해야 한다.

## 🚀 실행 (Execute)
- [ ] 현재 운영 중인 서비스/앱의 RLS 설정 점검 및 구체적 시나리오 기반 감사 수행
  - 담당: 개발팀장 또는 시니어 개발자
  - 이유: 사용자가 구독 상태나 다른 사용자 데이터에 접근할 수 있는 취약점이 있을 수 있음
- [ ] 백엔드에 사용자별 및 IP 기반 Rate Limit 설정 구현
  - 담당: 백엔드 개발자
  - 이유: 프론트엔드 제한은 쉽게 우회 가능하고, 스팸 요청으로 인한 요금 폭탄을 방지해야 함
- [ ] 민감한 API 키들의 백엔드 이전 및 예산 한도 설정
  - 담당: 풀스택 개발자
  - 이유: 프론트엔드의 API 키는 추출 가능하며, AWS나 AI API 남용으로 수만 달러 청구서를 받을 수 있음
- 자료: Supabase Edge Functions 문서 (백엔드 API 호출용)
- 자료: Firebase Functions 가이드
- 자료: Veracode AI 코드 보안 분석 도구 (확인 필요)
- 자료: 클라우드 서비스 예산 알림 설정 가이드
- Timeline: 1순위: API 키 백엔드 이전 (가장 위험), 2순위: RLS 감사 (데이터 유출 방지), 3순위: Rate Limit 구현 (서비스 안정성). 모든 작업을 2주 내 완료하되, API 키 이전은 이번 주 내 필수 완료.
